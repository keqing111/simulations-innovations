# 完整 GPU 级基线对齐与算法缺口

日期：2026-11-12。当前完成的是**基线实现、解析测试和有限开发面板**，不是正式实验矩阵或新算法。本轮不修改 FAST 匹配器、Local、Global、scaling 判据或网络模型。

## 1. 基线实现与执行边界

在现有 `simulation/bvn_decompose_main.cpp` 增加 `--mode spreadout`，不引入新的生产类。全局 GPU 数 R=N×G，第 offset=1..R−1 轮，GPU s 发给 `(s+offset)%R`，发送原始 GPU 对的完整实际数据量；每轮至多一发一收。

- 跨 server 流统一调用 `Topology::evaluate_gpu()`，与 FAST 使用同一共享端口/网关/有向WAN路径和容量近似。
- 同 server 流按原生 H100 参数：0.1us + 2.3us/MB × 实际流量。同轮机内与网络取 max，轮间串行；延续原仓库 spread-out 基线的轮转执行语义，不额外修改 FAST 依赖。
- FAST 保留自己的 Balance/dispatch/pipeline2，spreadout 不做 Balance。这是算法流程差异，不给 spreadout 免费执行 FAST 的重整。
- `--topology 0` 仅用于与旧独占 alpha-beta 基线对账；正式配对均为 `--topology 1`。旧基线时间额外输出，但不混入共享网络排名。
- 空轮不付通信时间，所有非零原始 GPU 对恰好发送一次；输入 GPU 对角必须为0。

这叫 **spreadout-like 仿真基线**，不是运行 NCCL，也不覆盖 NCCL 的实际并发、协议、流水线实现。当前模型同样不模拟动态逐流释放、队列与包级拥塞。

## 2. 冻结开发面板

N=8/16、G=4，严格均匀/循环微扰均匀/receiver-Zipf，沿用已有生成器与Zipf seed101。每GPU跨server预算39060单位（微扰增加1单位），分别采用每单位16B与1024B，对应每GPU约0.625MB与39.997MB；同server原始需求均为0。

3DC：`dc[s]=floor(3s/N)`；server与网关400Gbps、每有向DC对WAN100Gbps；同DC传播1.4us，跨DC52.8us。N不整除3时DC大小不同。原生 scaling 判据保留 ETHER400/H100 输入，不改成新设计的WAN感知判据。

每个需求同时运行 spreadout、S0/scaling关、S0/开、S1/关、S1/开；12个条件×5方法=60份输出，每份3次规划/模拟。S0是原生无权Kuhn，S1是最大瓶颈完整分解；二者都不读取拓扑。**没有按输入挑最好策略作为一个算法。**

## 4. 可以作为算法动机的明确缺口

### A. 倾斜需求在相同 K、相同 q 下仍有资源组合差距

N16、Zipf、16B单位、scaling开启：S0与S1均16阶段，每阶段原始单位系数均9341。真实资源总字节相同，传播总项均844.8us；但序列化阶段和为787.05664us与936.76032us。

S1完整时间1.782642ms，比S0的1.632955ms慢约9.17%。未隐藏的机内开销约1.10/1.08us，无法解释149.7us的差距。这里不能用“阶段太多”或“系数更小”解释，直接指向真实字节在共享资源上的阶段组合。

N8小负载Zipf也有相同8阶段、相同系数11765的差距，但传播项同时改变，因此不如N16控制干净。**N16案例可优先用于检验资源感知匹配，而非将优化限制到均衡需求。**

### B. 降阶段的收益可能伴随序列化退化

N16、Zipf、1024B单位，scaling开启但实际因子为1：

| 方法 | 活动阶段/轮数 | 传播阶段和us | 序列化阶段和us | 未隐藏机内us | 总时间ms |
|---|---:|---:|---:|---:|---:|
| S0 | 223 | 11671.6 | 59483.42272 | 8.43251 | 71.163455 |
| S1 | 91 | 4804.8 | 60199.40352 | 0.30707 | 65.004511 |
| spreadout-like | 63 | 3326.4 | 59646.36160 | 约0 | 62.972762 |

S1减少阶段、节省传播支付次数，但序列化反而增加约716us。最终仍比spreadout-like慢约3.23%；说明减少阶段与改善共享组合不能互相替代。spreadout允许同轮各GPU对不同发送量，FAST使用自己的重整和阶段系数，二者结构不同；不能将两者的阶段数差直接归咎于Kuhn，需区分原语约束与可改变的匹配选择。

### C. 原生 scaling 是必须保留的强对照

小负载Zipf下，原生S0开启scaling会将N8从48阶段降到8、N16从223降到16；完整时间分别从2.946250→0.848669ms、12.601456→1.632955ms。不能再把未缩放原生的全部碎片当作新增算法可独占的收益。

微扰均匀也可被原生scaling大幅改善。此前只有1024B负载的scaling控制并未揭示这一点；**本轮修正了“现有scaling控制已经足够”的范围判断**，而不是推翻原始有限面板的记录。

### 对算法设计的含义

这些结果是问题证据，不是新颖性证明。下一步优先在相同缩放/阈值可行图内，让共享资源信息直接指导匹配，检验能否修复案例A，并在案例B中避免以序列化损失抵消减阶段收益。所有评分都应使用真实剩余payload，虚拟补齐不能获得资源服务奖励。不能仅优化A而忽略最终完整操作时间及规划成本。

## 5. 正确性、开销与边界

- 新增6个回归测试：共享WAN/全双工、独立WAN、共享NIC、机内及混合轮次、空需求与旧模型对账、MB浮点转换后的资源核验。
- 首次批量审计遇到 `66224` 与 `66223.99999999999` 的double转换差，定位后只对物理浮点资源/时间采用相对1e-12、绝对1e-8容差。原始GPU交付和跨方案整数资源总量仍严格相等。新增该失败案例后通过回归。
- 每份spreadout输出逐GPU对严格守恒；每份FAST输出按原生语义核对服务器对守恒。Python独立重算每轮资源字节、传播、序列化和pipeline2递推；12个配对面板所有方法的真实资源总字节严格相同。
- `make -C simulation check bvn-check bvn-decompose-build` 通过：集成C++、12个Python测试、独立BvN的5443项检查。没有新增算法收益声明。
- FAST输出保留分解CPU与全规划墙钟；spreadout的 `simulation_cpu_samples_us` 包含模型评价与trace构造，不是纯规划CPU，**不直接与FAST分解CPU排名**。本轮尚未完成统一规划CPU口径。
- 本面板只有一种3DC资源配置、两种规模、一个Zipf生成种子及同server原始需求为0。混合机内流仅完成解析测试，尚未扩成完整FAST业务扫描；固定传播/容量近似、轮转执行假设与真实系统的差别明确保留。不能宣称已完成正式论文全部基线矩阵。
