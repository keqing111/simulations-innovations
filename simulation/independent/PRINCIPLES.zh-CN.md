# FAST 拓扑感知优化：原理、设计理由与代码对应

日期：2026-11-04。

本文只解释原生 FAST，以及我们分别实现的共享带宽策略 `bandwidth`、完成时间策略 `time`，不展开其他算法比较。所有公式使用普通文本，直接打开 Markdown 源文件也能阅读。

## 1. 一句话说明我们改了什么

原生 FAST 每轮寻找一个合法的服务器收发匹配；我们保留它的分解框架，但在同样合法的匹配中，尝试选择网络代价更小的一个。

两个方向分别回答不同的问题：

|方向|原生匹配没有回答的问题|新策略的选择依据|
|---|---|---|
|共享带宽|端点不冲突的流，会不会挤在同一个网关或同一条 WAN 上？|本阶段最忙共享资源的服务时间|
|完成时间|一个阶段必须等待多久，慢路径是否在过多阶段中重复出现？|本阶段最慢单条路径的预测完成时间|

两条策略独立运行，当前没有合并。它们改变的是“哪些服务器对在同一阶段发送”，不是改变原始需求、选择其他路由或提高物理带宽。

本文所说的“完成时间”是当前解析仿真模型的预测，不是实机测量或 ns-3 包级仿真结果。

## 2. 原生 FAST 的分解究竟在做什么

### 2.1 匹配只解决端点约束

把每台服务器复制成两个顶点：左侧表示发送端，右侧表示接收端。服务器之间仍有残余量时，就存在一条可选边。

一个完美匹配要求：每个发送端选一个接收端，每个接收端只被选一次。发送和接收是两个角色，同一台服务器可以同时向一个目标发送、从另一个源接收。虚拟补齐也可能产生自匹配槽位，但不代表真实网络传输。

代码里的 `hungarian()` 实际是无权的 Kuhn 增广路匹配，不是带权最小费用匈牙利算法。它会在目的端已占用时尝试改配，解决“能否组成合法匹配”，但不会比较这些匹配的拓扑费用。

因此原生的不足不是没有找出合法匹配，而是：**合法匹配之间可能有显著不同的网络代价，原生选择没有利用这个信息。** 原生邻接表使用无序集合，具体选择还会受其遍历顺序影响，不能把它理解成按带宽排序。

### 2.2 为什么每轮还需要一个公共分解量 q

FAST 先将服务器级矩阵补齐，使各行和各列的和相等。这保证残余未清空时可以继续找到完美匹配。这里把补齐后的当前残余矩阵简称为 A。

本轮原生匹配选出一组边，q 就是这些边上的最小残余量。例如：

```text
某个匹配选中了四条边，残余量分别为：100、150、100、200
q = min(100, 150, 100, 200) = 100

本轮从这四个矩阵位置各扣除100。
扣除后，至少有一个原来非零的位置变成零。
```

各行、各列都恰好减去 q，因而保留后续分解所需的结构。重复此过程，就得到“匹配 + 公共分解量”的阶段序列。

这里 q 是服务器级调度矩阵的系数，不能直接当成整个服务器对的真实发送字节。实际发送还要看每块 GPU 的真实剩余数据；补齐出来的虚拟量不能当成真实通信。

## 3. 为什么保留字节矩阵，另算拓扑代价

我们同时维护两类信息：

- 分解残余 A：回答哪些匹配合法、可以扣除多少公共量，包含原生补齐。
- 真实剩余数据 R：回答这次实际发送多少字节，不把虚拟补齐算成网络负载。

在公共量 q 下，一对服务器本轮发送的真实字节按原生派发方式预测：

```text
服务器对本轮字节 = 对源服务器的每块GPU求和：min(q, 该GPU发往目标服务器的真实剩余字节)
```

例如，两块 GPU 发往同一目标的剩余量是80字节和150字节，q是100，则本轮真实发送80 + 100 = 180字节，而不是200字节。该例仅说明派发计数，不代表一个完整分解输入。

为什么不直接把原矩阵乘 RTT 或除带宽？

1. 分解矩阵承担流量守恒的含义，直接换成时间会改变行列平衡与扣除单位，需要重新定义分解，不能再照搬原生字节派发。
2. 传播时间与串行化时间是相加，不是相乘。
3. 共享竞争取决于本阶段同时选择了哪些流，不是某个服务器对固定乘一个权重就能完整表达。

所以我们保留原始字节含义，用辅助代价指导匹配，再按原生方式实际扣除字节。这是对你提出的“用完成时间指导调度”的具体落实，而不是把真实数据膨胀。

## 4. 公共框架：先保留原生结果，再尝试替换

每轮的执行顺序如下：

```text
当前残余矩阵
    → 原生Hungarian生成匹配M0
    → 计算M0的公共量q
    → 根据一种拓扑目标生成候选M1
    → 检查保护条件
        → 通过：用M1
        → 未通过：保留M0
    → 原生记录阶段、扣除残余，进入下一轮
```

我们不是只在完整调度生成后重排阶段。修改发生在本轮扣除之前，所以它会改变后续残余矩阵及后续匹配。

### 4.1 三个接受条件，以及为什么设置它们

候选构造只允许使用“残余量至少为 q”的边，完整候选还必须满足：

|接受条件|设计原因|限制与代价|
|---|---|---|
|候选匹配的最小残余量恰等于原来的 q|先固定本轮分解粒度，隔离匹配选择的贡献；避免靠缩小 q 获取局部好分数|甚至会拒绝最小残余量大于 q 的候选；这是保守实验选择，不是正确性的必要条件|
|候选本轮真实跨服务器服务字节不少于原生|避免通过多选虚拟槽位、少传真实数据来降低代价|可能拒绝局部少传、长期更优的方案|
|本策略的目标值严格降低|当前阶段无明确收益时不改变原生结果|只接受一个构造出的候选；拒绝它后不会继续搜索全部其他匹配|

尤其要注意：比较对象是**当前残余上的原生匹配**。前面某轮发生改变后，当前残余已经可能不同于从头到尾运行原生 FAST 时的残余。

因此这些条件不意味着“每个阶段都比原生完整调度的对应阶段更快”，也不保证全程阶段数不增加。

### 4.2 能保证什么，不能保证什么

只要选中的仍是正残余支持图中的完美匹配，再扣除匹配最小残量，就保留标准分解的推进方式。每轮至少清零一条正边，零边不会重新增加，所以阶段数至多为初始正边数，也就是至多服务器数的平方。

这是有限性上界，**不是人为规定“最多几个阶段然后在其中求全局最优”**，更不是实用的阶段数不增加保证。

代码还检查最终真实跨服务器剩余量是否全部为零，并核对预测派发量与原生实际派发量。不满足就报错，不输出成功结果。机内调度仍沿用原生历史语义，不声称重新证明了原生完整机内算法的正确性。

## 5. 方向一：共享带宽资源感知

### 5.1 先识别共享资源，再计算阶段瓶颈

端点不冲突不代表路径不冲突。例如，两条来自不同服务器、发往不同服务器的流，也可能一起经过 DC0→DC1 的 WAN。

当前拓扑模型将以下内容表示为带宽资源：服务器发送端口、服务器接收端口、网关发送资源、网关接收资源、有向 DC 对的 WAN。相反方向的 WAN 分别计量。当前模型没有额外建立独立 TOR 内部交换容量，也不模拟队列、ACK、PFC或DCQCN。

```text
某资源本阶段负载 = 所有经过这个资源的真实流字节之和
某资源服务时间 = 8 × 资源负载字节 ÷ 资源带宽（bit/s）
本阶段带宽代价 = 所有资源服务时间中的最大值
```

取最大值的原因是各资源并行工作，阶段受最慢资源限制。不能把每个资源的服务时间全部串行相加，也不能忽略流在共享资源上的叠加。

### 5.2 如何修改增广路的选择顺序

本策略复用资源缓存中的增广构造，从空匹配生成一个完整候选，处理源服务器的顺序仍是自然编号，当前没有实现拓扑感知的源服务器排序。

它与原生 DFS 的主要区别是：在尝试目的服务器之前，先给候选排序。

1. 记录当前部分匹配已占用的各资源字节。
2. 为当前源服务器列出残余量至少为 q 的候选目的服务器。
3. 估算加入每条候选边后的最大“资源负载÷带宽”。若当前源已经有旧配对，估算前先移除它自己的旧占用，避免重复计数。
4. 优先尝试峰值较小的候选。
5. 峰值相同时，优先选择资源归一化负载平方增量较小的候选。
6. 目的端若已占用，则像原生一样递归尝试将原来的源改配到别处；成功后才提交资源负载变化。
7. 生成完整候选后，重新计算完整匹配的瓶颈服务时间，执行保护和验收。

增广路的简单例子：源A希望匹配目的B，但B当前匹配源C；若C可以改去目的D，就将C→B替换为C→D，再加入A→B。我们改变的是优先尝试哪些边，仍用这个机制维护合法性。

平方增量只是破平局项。例如，两个资源的归一化负载为4和1，增加同样1单位负载：加到前者，平方增量是25−16=9；加到后者，是4−1=3。优先后者可以避免只因当前最大值没变，就继续向已经偏忙的资源堆积流量。这是启发式，不是全局最优证明。

### 5.3 为什么这样设计，而不是枚举或求解器

共享资源代价与多个配对共同有关，通常不能简单拆成固定的独立边权。我们希望保留在线规划的低开销，因此复用增广路，只加入部分负载排序，并只生成一个完整候选，不枚举服务器排列，也不引入全局优化求解器。

构造时的局部判断会被后续增广改配影响，所以必须对完整候选再验收。即使验收通过，也只代表本轮带宽目标改善，不保证整个分解的最优性。

本策略构造和验收都不使用传播时延。这是为了先单独验证共享带宽这个机制，不是认为时延不重要。

### 5.4 一个局部示意，不是完整守恒反例

两条不同端点的100 MB流，若共用一条100 Gbps WAN，该资源承担200 MB，服务时间约16 ms；若合法匹配可以让两条流分别使用两条独立的100 Gbps WAN，峰值约8 ms。

该示意解释为什么某一阶段的匹配会有带宽差别。它本身没有列出完整需求与后续阶段，不能单独据此证明整次通信提速。完整可复核输入见[原生不足反例](../topology/COUNTEREXAMPLE.md)。

## 6. 方向二：单路径完成时间感知

### 6.1 边代价为什么是传播加串行化

```text
候选边时间 = 单向路径传播时间 + 8 × 本轮真实字节 ÷ 路径最小带宽
```

“串行化”指把全部数据逐位送入链路所需的时间；“传播”指信号沿路径到达接收端所需的时间。简单流水传输中，最后一位到达需要考虑这两个分量。

例如100 MB经过100 Gbps瓶颈，串行化约8 ms；路径单向传播5 ms，则独立流预测约13 ms，不是把8 ms与5 ms相乘。

这里取路径最小带宽，因为单条流不能长期以高于瓶颈的速率通过整条路径。它是当前解析模型下的近似，不是完整 TCP/RDMA 流完成时间公式；没有加入额外握手、窗口、拥塞和逐跳整消息存储转发费用。

若代码中带宽用 Gbps、数据用字节、时间用微秒，对应写法就是：

```cpp
cost = path_alpha_us + 0.008 * real_bytes / path_min_bandwidth_gbps;
```

自匹配和零真实字节的边代价为零，不能只因为虚拟位置跨 DC 就计入 WAN 传播时间。

### 6.2 为什么最小化最慢边，而不是所有边代价之和

同阶段的路径并行执行。仅从独立路径角度看，阶段完成需要等待最慢路径，而不是所有路径的时间之和。

例如三条并行路径分别需要1、1、10 ms，另一个方案需要4、4、5 ms。后者时间总和更大，但其最大值更小，独立路径模型下阶段完成更快。因此本策略寻找的是“最小最大值”的匹配，而不是最小费用和匹配。

### 6.3 阈值二分与增广路怎样求解

固定本轮 q 后，候选边的独立路径费用已经确定：

1. 将所有可选边费用排序并去重。
2. 选一个费用上限，例如8 ms。
3. 只允许使用“残余至少为 q，且边费用不超过8 ms”的边。
4. 用普通增广路检查能否形成完美匹配。
5. 如果可以，降低上限；如果不可以，提高上限。
6. 二分找到最小可行上限，并取对应的完整匹配。

这个搜索成立，是因为提高费用上限只会增加可用边，不会删除边：一个上限可行，更高上限也可行。

它精确求解的是**本轮受限支持图上的最小最大边费用**。最终仍需要通过分解量和真实服务量保护，因而可能拒绝求出的候选。它既不搜索所有未来阶段，也没有证明整个 all-to-all 最优。

选择该方法的原因是：比逐边贪心更准确地解决这个本轮目标，同时可复用无权增广路，不需要排列枚举。每轮需要多次可行性匹配，确实有额外成本，不能仅凭未使用求解器就称其开销等同原生。

### 6.4 为什么它可能减少 WAN 传播的重复暴露

原生匹配不区分近端与远端路径，可能让很多阶段都含 WAN 流。若合法分解允许把 WAN 流组织在较少阶段中，其他阶段仅做 DC 内服务器间传输，就可能减少累计远端传播等待。

当前实现没有硬编码“先做LAN”或“WAN阶段越少越好”。它只是每轮尝试降低最慢单路径费用，上述阶段组织是可能产生的结果，不是保证。

这也说明早先“只要还有WAN数据，每个阶段都应包含WAN”的直觉不能当作通用规则：那可能维持链路活跃，却增加慢路径在阶段计时中的重复暴露。当前两条实现都没有强制该约束。

## 7. 公共计价器、等待规则与策略目标不能混淆

原生和改进策略都使用同一个拓扑计价器，不能给新策略换一个有利的计时公式：

```text
阶段网络时间 = 最慢活跃路径传播时间 + 最忙共享资源服务时间
```

网络阶段时间再交回原生 `pipeline2`，与原生机内 balance、dispatch 等费用按既有方式组合。我们没有新增全局 barrier，也没有实现独立 rank 提前释放、跨网络阶段重叠的新事件调度器。

当前模型按阶段组合网络费用；减少重复暴露的收益应解释为这个模型里的收益，不能直接宣称现实中每个阶段都会额外进行一次显式同步。跨阶段流水更充分时，这种收益可能不同，当前没有另行验证。

还需要区分两个不等价的量：

- 时间策略构造目标：各条路径“传播 + 独占路径串行化”的最大值。
- 公共阶段计价：最大路径传播，加上考虑全部并发流后的最大资源服务时间。

传播最大值和资源最大值甚至可能来自不同路径；此外，独立路径费用不知道其他流占用了多少共享资源。因此时间策略降低构造目标后，公共计价器算出的阶段时间仍可能增加。

快流先完成而等待慢流，确实存在局部空闲；但局部空闲不等于可消除的总时间损失。如果把快流另放一个阶段，可能要额外付出阶段时间。应比较完整合法调度的总完成时间，而不是仅以是否有空闲来判断好坏。

## 8. 设计为什么可能失效：必须主动承认的边界

### 8.1 带宽策略不知道后续残余的全局后果

当前阶段负载分散了，但扣掉这些边后，后面的残余可能更难分散。于是本轮瓶颈下降，累计瓶颈时间反而增加。回退规则没有查看完整后续分解，不能防止这种负收益。

### 8.2 时间策略看不到并发共享竞争

它可能少暴露一次传播，却把更多流放到同一个网关或WAN上。如果新增共享服务时间超过减少的传播时间，总完成时间就会变差。这不是可以忽略的噪声，而是单路径目标与公共计价器不一致的明确限制。

### 8.3 限制本轮 q 是保守选择，不是最优选择

本轮 q 相同，有助于隔离拓扑选择贡献，但会缩小搜索空间。阶段数仍可能变化；即使阶段数不变，累计费用仍可能增加。当前没有全局非退化保证，也没有自适应地放宽这些保护。

### 8.4 拓扑固定，为什么还要逐轮计算

路径、带宽、传播时间可以缓存；但当前匹配、每条边本轮真实字节、各共享资源累计负载都会变化。

所以缓存的是“谁会经过哪些资源”，不是缓存一个永远不变的共享费用。带宽策略的动态性恰恰来自同阶段流的组合。

## 9. 已有实验说明了什么

以下来自已有运行，不是本文新启动的实验。两个机制输入均为6服务器、3DC、每DC两台、每服务器1GPU；所有不同服务器对各100,000,000字节；WAN单向5 ms。

|案例|原生 FAST|对应独立优化|观察|
|---|---:|---:|---|
|带宽受限：服务器/网关/WAN为400/400/100 Gbps|81.0140 ms|带宽策略54.0126 ms|累计瓶颈服务56→34 ms；累计传播也减少约5.0014 ms，不能把全部收益归为带宽|
|传播受限：400/800/800 Gbps|35.0140 ms|时间策略30.0126 ms|总阶段数仍为5，WAN阶段5→4；累计瓶颈服务仍为10 ms|

第二个输入中，每DC的网关和每有向WAN可承接两台400 Gbps服务器，不再额外压低端点并发能力。时间策略实际产生了一个纯DC内服务器通信阶段，并非机内 scale-up 阶段。

24组小扫描中，带宽策略相对原生的配对加速比几何平均为1.0826倍，8胜12平4负；时间策略为1.0794倍，22胜2负。这些配置只复用了6个不同rank矩阵，不能当成24份独立随机样本。

一个共同负例是12服务器、Zipf种子860201、共享WAN、单向50微秒：原生20.1140 ms，带宽策略20.6854 ms，时间策略20.5594 ms。三者总阶段数都是115。

- 带宽策略累计瓶颈服务14.1406→14.7099 ms，累计传播相同，体现后续残余变差的风险。
- 时间策略累计传播5.9178→5.8664 ms，但累计瓶颈服务14.1406→14.6375 ms，新增服务时间超过节省的传播时间。

因此目前合理结论是：两个优化方向都有可复核的作用机制，但这两个具体局部算法尚不能保证普遍提速。本文不以其他算法比较替代对原生 FAST 的机制解释。完整输入、原始数据与验证范围见[实验报告](REPORT.md)。

为避免覆盖正在批注的源码，本轮新增策略位于 `simulation/independent`，编译时使用冻结的原生研究引擎。阅读时需要同时看新增模块和它实际调用的冻结依赖，不能只在主目录的 `hungarian_dfs()` 中寻找全部修改。

|8|[构建脚本](build.py)|实际编译哪些冻结源码和新增模块|

对应核心伪代码如下。带宽与时间分支每次只启用一个：

```text
补齐矩阵，保持真实字节单独存储

每轮：
    M0 = 原生Hungarian在当前残余上得到的匹配
    q = M0匹配边的最小残余量
    可选边 = 残余至少为q的边

    如果启用带宽策略：
        M1 = 按部分共享资源峰值排序，用增广路构造一个匹配
        目标 = 完整匹配的最大资源服务时间
    如果启用时间策略：
        边费用 = 传播 + 本轮真实字节的独占路径串行化
        M1 = 用费用阈值二分和增广路找到最小最大边费用匹配
        目标 = 匹配中最大的边费用

    如果M1的最小残余恰等于q、真实服务量不少于M0、且目标严格改善：
        选M1
    否则：
        选M0

    写回选中的匹配
    更新真实剩余量影子
    由原生分解记录阶段并扣除匹配最小残量

检查全部真实跨服务器字节都已派发
用相同拓扑模型和原生pipeline2评价调度
```

总结：带宽方向是在增广匹配中补充“这组流共享什么资源”；时间方向是在匹配中补充“这组流的最慢独立路径需要多久”。保留原生分解，是为了保持合法性、复用快速规划框架；单独实现和保守验收，是为了先弄清机制，而不是已经证明这些具体设计就是最终最优算法。

## 11. 建议的后续两步

1. 对机制输入逐阶段导出原生与改进的匹配、真实字节和资源负载，把上述选择逻辑落实为可逐项核对的轨迹。
2. 用同样轨迹分析共同负例，再决定是否联合两种目标、放宽q保护或引入有限前瞻；暂不把这些尚未实现的设计算作现有创新。
