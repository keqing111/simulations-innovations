# 研究主线、基线与组合验证

日期：2026-11-11。目标是解释异构多级固定路径下的 A2A 调度，不预设所有优化组合都有效。本文明确区分：已经验证的现象、受限研究原型、尚未完成的论文实验。

## 1. 基线怎么定

**主基线定为原生 FAST，补充基线采用 spreadout-like。两者不是二选一。**

| 名称 | 实际运行内容 | 回答的问题 | 当前状态 |
|---|---|---|---|
| FAST-native | 当前仓库已核验的原生 Balance、补齐、Kuhn 分解、dispatch、pipeline2；调度不读取拓扑，共用同一个物理评价器 | 相对原生方法，修改是否改善完整操作？ | 已有独立规模实验；本轮组合尚未接完整流水线 |
| FAST-native-no-scale | 上述原生路径，但关闭原生 scaling | 只改变匹配选择，收益来自哪里？ | 当前完整策略消融采用此口径，不能作为唯一强基线 |
| Spreadout-like | GPU/rank 按循环偏移轮转，每轮每个 rank 至多一发一收，各通信对发送自己的实际剩余量 | 是否只打败了一个容易碎片化的 BvN 实现？ | 本轮先做 G=1/server 端点网络参考；完整 GPU 级对照待补 |
| FAST-BvN 原生分解 | 只复用 FAST 原生补齐和 Kuhn；移除 Local 与流水线，仅评价网络阶段和 | 分解质量、拓扑组合的机制能否隔离？ | 本轮实验的主对照，**不简称为完整 FAST 加速实验** |

正式完整操作实验同时报告原生 scaling 开/关，并让对应改进使用相同开关；不通过关闭原生 scaling 来人为削弱 FAST。后续应固定原生 scaling 的接受规则和数值单位，不按测试结果逐案例挑选最有利模式。

Spreadout-like 是明确写出的轮转仿真算法，**不是 NCCL 库运行结果，也不声称复现了 NCCL 的实际算法选择和实现性能**。当前仓库 `scheduler/config.cpp::spread_out_baseline()` 使用独占 alpha-beta 计价，不能直接拿它与共享 WAN 评价器的结果比较；正式拓扑实验应复用轮转规则，但所有方案采用同一拓扑计价。Direct 不作为主要性能对照。

公平性要求：同一真实 GPU 需求、固定路径、带宽、传播假设、机内模型、阶段执行语义和资源计价；方法不同可以有不同阶段数，不能给某个方法额外免费跨阶段重叠。完整 FAST 和 spreadout 的机内处理各按自己的流程计费，不强行套相同的 Balance。报告通信时间、规划 CPU 和必要时串行预算，不能将通信加速冒充包含 CPU 的端到端加速。

## 2. 论文应该讲什么问题

不建议用“FAST 不考虑拓扑，所以加入拓扑会更快”作为完整故事。它没有说明哪个决策错了，也解释不了何时没有收益。

更准确的研究问题是：

> 端点可行且阶段数较少的 BvN 分解，仍不一定让共享资源高效并行。能否在限制规划成本和分解碎片的前提下，按共享资源及阶段传播成本组织通信组合？

它包含两类不同损失：

1. **分解碎片损失。** 任意完美匹配可能提前抽走某些边的小残量，形成许多后续细碎阶段。在阶段串行模型中，传播/启动类固定项会重复支付。最大瓶颈匹配倾向于提高提取粒度，但不保证全局阶段数最小，甚至不保证不增加阶段数。
2. **资源组合损失。** 即使阶段数、系数序列、消边数完全相同，不同通信对的组合仍会改变每阶段最繁忙共享资源的工作量。阶段数代理无法区分这些调度。

两类损失可以互补，但不能从“分别有效”推导出“直接拼接必然有效”。减少碎片可能改变可交换结构；共享资源优化也可能破坏大系数匹配。算法必须解释自己保护了什么、允许改变什么。

最大瓶颈、最大消边、最大度下降是**比较对象和设计工具**；不能仅凭采用这些已定义的匹配目标就声称足够的论文原创性。当前候选贡献应集中于“分解可行性/粒度约束下的拓扑资源组合”，是否有足够新颖性还需与相关工作逐项核对。

## 3. 采用什么模型解释收益

当前网络阶段模型为：

```text
某阶段的序列化代价 = max over 链路资源 (该资源本阶段聚合真实字节 / 资源带宽)
某阶段的传播代价   = max over 活动真实路径 (单向传播时延)
网络阶段和         = sum over 阶段 (序列化代价 + 传播代价)
```

代码以字节、Gbps、us 换算，序列化项为 `0.008 * bytes / Gbps`。RTT 只作元数据，不与单向传播混用。固定路径下资源总字节不因调度改变；收益来自改变各阶段资源工作量的最大值、传播项的支付次数及后续可能的流水线重叠，而不是凭空减少瓶颈必传字节。

这是容量近似，不是逐流完成时间、包级仿真或链路忙闲实测。尤其 `max(传播)+max(资源工作量)` 的两项可能由不同流决定。当前证据首先证明**在该模型内**的因果关系；不能把资源工作量/总时间称为实测 WAN 利用率。

### 什么时候该分散 WAN，什么时候该集中？

已有两 DC 均匀解析族中，N=2m、K=2m−1、每对 Q 字节，所有分解的 K/q/Z/最大度演化相同。设 L 为包含 WAN 通信的阶段数：

```text
c = 单条 Q 字节流在 100Gbps WAN 上的序列化时间
e = 单条 Q 字节流在 400Gbps 端口上的序列化时间
T = m²*c + K*(e + tauLAN) + L*(tauWAN - tauLAN - e)
```

因此 WAN 持续出现在更多阶段并非普遍最优：传播差小于 e 时，增加 L 有利；传播差大于 e 时，减少 L 有利。LAN=1.4us、WAN=52.8us 时转折为 Q=2,570,000B。该结论针对这个解析族与模型，不是通用网络临界公式。细节与实际计划见 [动态小例报告](DYNAMIC_SMALL_REPORT.md)。

这比“尽量让 WAN 每阶段有流”更适合作为论文 insight：**共享资源并行与阶段固定成本存在竞争，调度应根据负载规模选择资源组合。**

## 4. 本轮实际试了什么组合

新增研究脚本 [combination_pilot.py](combination_pilot.py)，未改生产匹配器、补齐、Local、Global 或已有数据。

先使用相同原生补齐矩阵生成四种完整分解：

| 编号 | 匹配选择方式 |
|---|---|
| S0 | FAST 原生无权 Kuhn |
| S1 | 最大可行瓶颈阈值，再取该阈值下的完美匹配 |
| S2 | 在至多 8 个阈值上求最大等阈值消边数的带权指派 |
| S3 | 在至多 8 个阈值上尝试消除所有最大度端点的边，不可行则回退 S1 |

分别对每个分解叠加同一受保护拓扑调整，构成“原生/改进分解 × 不调整/拓扑调整”消融。调整规则是：

1. 只查看相邻两个系数 q 完全相同的完整匹配。
2. 在两匹配并图的交替环中，交换一个完整的非平凡环在两阶段的归属；只有单个环时，交换只是倒序，不尝试。
3. 检查两个新阶段顺序执行时的**实际最小残量仍分别等于原 q**。
4. 检查窗口后辅助残余、真实残余、逐对字节完全相同。
5. 只有同一拓扑模型下两阶段总代价严格下降才接受。每份计划最多尝试 64 次，不重启完整分解。

这个操作不删真实需求、不改 q、不增减 K。等 q 保证 `q(P+Q)=q(P'+Q')`；窗口后的状态相同，故原后缀仍成立。因此它保护的是相对**自身分解方案的网络阶段和**，不是相对原生 FAST、不是包含 CPU 的总耗时，也不是完整 pipeline2 的非退化保证。

它仍是有界的局部诊断工具，不是已确定的最终在线算法。不能因该工具在严格护栏下没有回退，就声称实现了普适最优匹配。

## 5. 冻结实验配置

- N=8/16，G=1 的服务器级端点网络实验，不执行 GPU Balance/dispatch。
- 严格均匀：每源 9765KiB；微扰均匀：在循环后继需求上额外加 1KiB，每源 9766KiB，仍等行列和。
- 合成 receiver-Zipf 指数 0.9、生成种子 101，每源 9765KiB。额外 placement102/103 同时重编号所有行列，改变流量相对拓扑的位置，**不是额外独立流量种子**。
- 3DC，`dc(s)=floor(3s/N)`，故 DC 大小不完全相同；端点/网关各 400Gbps，每有向 DC 对 WAN 100Gbps，反向为独立资源。
- 两个传播控制：所有活动路径 1.4us；或者同 DC 1.4us、跨 DC 52.8us。路径与容量不变。
- 10 份主需求 × 4 策略 × 2 传播配置 = 80 份配对评价。
- 另加已有四 DC 独立 WAN 手工机制控制 × 4 策略 × 2 配置 = 8 份。单独列出，不混入总体提升。
- S2/S3 阈值预算 8；原生 scaling 关闭以隔离匹配；每个原生分解运行 3 次，核对计划相同并保留 CPU 样本。物理模型确定性输出不作重复采样置信区间。

## 6. 结果：互补有证据，但 Zipf 的拓扑增益仍弱

下表全部是 **N16、3DC、跨 DC 52.8us、placement101**，单位 ms。K 是辅助完整分解的阶段数；本表这些计划的真实活动阶段数与其相同。时间不含规划 CPU，也不是完整 FAST A2A 时间。

| 需求 | 原生分解 K / ms | S1 K / ms | 原生 + 拓扑调整 ms | S1 + 拓扑调整 ms | Spreadout-like 活动轮数 / ms |
|---|---:|---:|---:|---:|---:|
| 严格均匀 | 15 / 3.618486 | 15 / 3.511826 | 3.511826 | 3.298506 | 15 / 3.511826 |
| 微扰均匀 | 104 / 8.212255 | 15 / 3.565238 | 8.211927 | 3.405248 | 15 / 3.511908 |
| receiver-Zipf | 222 / 15.948882 | 83 / 8.509284 | 15.948882 | 8.508710 | 15 / 4.880955 |

![N16 分解与拓扑消融，线性纵轴](combination-results-20261111/mechanism_ablation.png)

### 收益来自哪里，而不只是加速多少

**严格均匀：资源组合。** S1 的 K=15、传播总项 0.792ms 完全不变。叠加拓扑调整后，序列化阶段和从 2.719826ms 降到 2.506506ms，网络阶段和减少 6.07%。因此该例收益不能归因于减少阶段，也不是少支付传播项。

**微扰均匀：先减碎片，再改善组合。** S0→S1 的 K 从 104 到 15，传播总项从 5.4912ms 降到 0.792ms；但序列化项反而从 2.721055ms 略增到 2.773238ms。再加拓扑调整，将序列化项降到 2.613248ms。这是两类机制可以互补的直接消融证据，不能把第一步所有收益归到拓扑。

**Zipf：主要仍是减少传播支付次数。** S0→S1 的 K 从 222 到 83，传播项从 11.6702ms 降到 4.3824ms，序列化项仅从 4.278682ms 降到 4.126884ms。拓扑调整进一步只减少 0.57344us，远不足以称为显著的 Zipf 拓扑优化。

四 DC 机制控制仍可在 K=2、q=(1,1) 不变时将 338.34432us 降到 191.54368us；长传播控制为 10341.14432→5192.94368us。这证明机制确实存在，但属于预先构造的解释性案例，**不能拿接近 2 倍的手工例当普遍性能结果**。

### 配对面板摘要，不隐藏失败

以下速度比均为“原生分解网络阶段和 / 对应方案网络阶段和”，越大越好；表中几何均值只是冻结小面板的描述，不是总体统计结论。排除四 DC 手工控制。

| 需求 | 配对数 | S1 速度比几何均值 | S1 + 拓扑调整速度比几何均值 | 拓扑调整相对 S1 的额外速度比 |
|---|---:|---:|---:|---:|
| 严格均匀 | 4 | 1.01717 | 1.05437 | 1.03658 |
| 微扰均匀 | 4 | 1.27715 | 1.31108 | 1.02657 |
| Zipf，各位置 | 12 | 1.20302 | 1.20317 | 1.00013 |

- S1 + 拓扑调整在 12 个 Zipf 配对中相对原生有 10 胜、2 负，速度比范围 0.86148–1.87442；不能说最差也是原生水平。
- Zipf 拓扑调整本身 6/12 有严格改善，但最大额外速度比也仅约 1.000849；“有几份改善”不等于有实用幅度。
- 所有策略的 Zipf 窗口总计 4002 个，其中相邻等 q 窗口只有 188 个，约 4.70%；其余 95.30% 被当前护栏跳过。资源信息主要用于接受评价，未充分改变异 q 情况的匹配生成，这是当前工具的明确局限，而不是证明 Zipf 不适合拓扑优化。
- 均匀 N8 的 S2 即使 K=7，物理时间也比原生更差；S2 在本轮所有面板均未被该小邻域改善。不能将四种分解看成性能等价。
- **本轮 Zipf 中，spreadout-like 快于 S1 + 拓扑调整。** 这不是完整 GPU FAST 的最终排名，但足以阻止我们现在宣称“相对有代表性的 A2A 基线全面有效”。必须保留这条补充对照，不能因为排名不利就撤掉。

### 规划开销不可省略

研究脚本的拓扑调整是 Python 实现，含合法性检查，不能与 C++ 分解 CPU 直接作实现效率结论。例如上表均匀 N16：S1 C++ 分解 CPU 中位数约 64us，而 Python 调整约 4122us，通信阶段只减少约 213us。因此当前原型**尚不能证明保持了在线优势**。需要在最终算法确定后做有界 C++ 实现，再测包含路径预处理、匹配、拓扑评分的规划成本。

## 7. 如何组织论文第 2/3/4 章

### 第 2 章：问题与动机

给出端点约束、固定路径共享资源、真实/虚拟需求的区分及阶段执行语义。用两个小案例分别证明：

1. 大系数或低阶段数不是全局最优的保证；
2. 即使 K/q/Z 相同，独立瓶颈的并行组合仍会不同。

用上述两 DC 转折式解释“WAN 更连续”并非唯一目标。不要将传播时延说成与带宽完全同类的可共享容量资源。

### 第 3 章：方法

先定义要保护的分解粒度/复杂度边界，再定义资源目标，而不是堆几个策略名字。当前可写清楚的只是研究原型：固定分解系数的两阶段交替环重排、合法性条件、逐对守恒及网络阶段和的局部接受证明。完整 FAST 的接受条件必须另含受影响的 dispatch/网络重叠项；本轮没有实现，不作保证。

S1 可作为减少碎片的基础模块，S2/S3 保留为候选消融；是否作为主算法组成部分，应由机制、开销和正式基线结果决定，不由某个手工例的最大加速决定。

### 第 4 章：评估

主性能图采用完整 FAST-native 与 GPU 级 spreadout-like，同一拓扑评价器；消融图采用原生/S1 × 无拓扑/拓扑调整。每图明确 K、通信 ms、规划 CPU ms、是否含流水线。分别改变倾斜程度、每源字节、共享资源容量、传播差、端点放置与规模，报告平均/几何均值及最差退化，不只展示最有利例子。

不需要为“故事好看”立刻扩成大网格。当前优先把 Zipf 的拓扑介入、完整执行模型和强基线打通；否则更多数据只会重复已知的局限。

## 8. 验证与后续优先级

本轮完成：

- 新脚本 5 个测试先因缺少接口失败，实现后全部通过，覆盖虚拟流过滤、实际最小系数、守恒重排、零预算与轮转异大小流。
- 88 份原生/调整计划均独立重放，不导入新脚本的评价函数，核对完美匹配、实际 min、真实逐对交付、资源总量及物理计价。
- `make -C simulation check bvn-check bvn-decompose-build` 通过：集成 C++ 测试、3 个历史 CLI 测试、独立 BvN 的 5443 项检查。
- 结果：[combination-results-20261111](combination-results-20261111/)，元数据 `complete=true`；同一运行中研究源码与分解二进制 hash 未改变。

复现：

```bash
make -C simulation bvn-decompose-build
python3 ds/decomposition/combination_pilot.py --self-test
python3 ds/decomposition/combination_pilot.py --out /tmp/bvn-combination-new
```

输出目录必须不存在；不覆盖旧结果。主要接口在脚本 `evaluate()`（辅助/真实分开重放）、`refine()`（有界两轮重排）、`spreadout()`（G1 轮转网络参考）。

接下来三项按优先级推进：

1. **完成强基线对齐。** 在完整 GPU 需求上比较 FAST-native scaling 开/关与 GPU 级 spreadout-like；统一共享拓扑评价，明确流水线代价。这是论文性能主张的入口条件。
2. **修正拓扑介入位置。** 针对 Zipf 大量异 q 阶段，探索分解系数/残余约束下直接生成资源感知匹配，而不是扩大事后删插搜索。先给出有界计算与守恒条件，再做小消融。
3. **将解释性证据固定下来。** 保留本文两个因果维度、WAN 传播/序列化转折和静态时间映射失败机制；正式评价同时检验成功区与失效区，再决定最终贡献边界。

目前可以讲清楚一个有证据的研究动机，还不能据此宣称已经具备足够的 EI 论文性能与在线开销证据。
