## 2. 从输入到结果的完整调用路径

```text
corrected_study.traffic：独立合成GPU向量计数，记录自身expert路由
  → host_vectors：乘8192，先转字节，再进入原生整数规划
  → runtime_host_reference：调用原始NVIDIA run_scheduler
       balance + server代表矩阵 + 补齐 + Kuhn/BvN + 降序 + restore
  → 导出原生真实payload、辅助容量、机内搬运矩阵和数据来源
  → joint_resource.State：分别恢复辅助R与真实待发U，读取固定路径
  → joint_resource.plan：逐轮联合选匹配P与实际系数q
  → runtime_host_reference replay：在全新Local状态上用原始helper回放候选
  → corrected_study.evaluate：统一解析拓扑和机内流水线计价
  → corrected_analysis：重新生成输入、检查交付/守恒/计时和汇总
```

这是一批计划的一次性生成与CPU数据量回放，不是运行中根据真实网络完成事件重新规划。网络阶段计价沿用既定解析模型；没有新增跨阶段全局barrier，也没有借此声称复现CUDA chunk执行。

### 2.1 原生FAST究竟保留了什么

- GPU到服务器需求汇总与平均目标：[prepare_load_balance](../../nvidia/src/fast_alltoall/alltoall_local_scheduler.cc#L129)。
- 机内负载搬运：[balance_one_server](../../nvidia/src/fast_alltoall/alltoall_local_scheduler.cc#L164)。
- 服务器矩阵补齐：[to_scaled_doubly_stochastic_matrix_fastall2all](../../nvidia/src/fast_alltoall/alltoall_algorithm.cc#L29)。本轮不额外调用旧仿真器的整数quantization搜索。
- 任意合法匹配与最小系数扣减：[decompose_fastall2all](../../nvidia/src/fast_alltoall/alltoall_algorithm.cc#L80)、[hungarian_dfs_fastall2all](../../nvidia/src/fast_alltoall/alltoall_algorithm.cc#L115)、[update_permutation_sets_fastall2all](../../nvidia/src/fast_alltoall/alltoall_algorithm.cc#L176)。
- 原生执行系数降序、intrinsic需求及逐阶段restore：[run_scheduler](../../nvidia/src/fast_alltoall/alltoall_global_scheduler.cc#L445)、[restore_one_server](../../nvidia/src/fast_alltoall/alltoall_local_scheduler.cc#L227)。

适配器：[extract](runtime_host.cpp#L46)用原始分解器额外导出容量；[compose](runtime_host.cpp#L77)只连接原始balance/restore；[main](runtime_host.cpp#L93)实际调用原始调度器，并比较整个`scheduling_result_t`与重放结果。逐原始GPU源和目的的数据重构也在这里进行，而不只是检查server总量。

**生成与执行不同**：生成每轮必须取所选边的实际最小残量；执行一个已经完整分解的计划时，允许重排，只需0<q<=所选剩余最小值且最终完整重构。[validate](runtime_host.cpp#L60)采用执行约束；原型[State.action](joint_resource.py#L141)采用生成约束。

## 3. 已实现的优化路线，分别解决什么

### 3.1 路线A：只优化分解粒度的三个既有C++策略

策略定义在[DecompositionStrategy](../../simulation/algorithm/all2all.h#L48)，统一执行循环在[decompose(options,...)](../../simulation/algorithm/all2all.cpp#L378)。四者共享补齐、实际最小系数扣减和整数重构；S1/S2/S3不是三个独立新贡献。

| 策略 | 本轮具体怎么选匹配 | 忽略的主要内容 |
|---|---|---|
| S0 原生Kuhn | 在正支持图中找到任意完美匹配 | 不评价中间共享资源 |
| S1 最大瓶颈 | 对正残量阈值二分，最大化匹配中最小值q | 大q不一定减少总K；不评价共享链路组合 |
| S2 最大消边数 | 有限阈值上做真正0/1费用Hungarian，优先消除更多等于q的边 | 消去的是辅助边，含虚拟容量，不等于完成同样多真实流 |
| S3 残余度下降 | 优先让所有当前最大度端点的匹配边都在本轮消失，失败回退S1 | 优化剩余stage数下界，不直接优化物理完成时间 |

这些方法提供分解粒度的对照和启发。此前的性能表不能直接代入本次修正后的GPU负载/原生CPU基线；本轮78组**没有重新证明S1/S2/S3的普遍收益**。

### 3.2 路线B：在固定最大q之后修补共享资源组合

旧C++实现先由S1确定最大可行q，再用共享资源费用生成匹配方向，或用2交换/3交替环严格降低本阶段资源代价。配置在[DecompositionOptions](../../simulation/algorithm/all2all.h#L54)，由[GlobalScheduler::set_decomposition](../../simulation/scheduler/global.cpp#L155)传入，接入`pipeline2`。

优点是易与S1比较、保证修改后q不变。缺点是如果最大q支持图中几乎只有一种匹配，拓扑修补根本没有自由度；本阶段代价下降也不保证后续更好。它是本轮联合原型的前一阶段，不是最新方法的别名。

### 3.3 路线C：联合选择提取粒度、共享资源组合与剩余工作（本轮主线）

不再把S1的最大q作为硬约束。先寻找可行阈值范围，再在最多4个阈值下进行资源指导的带权指派，对每个匹配重新计算实际q和真实发送量。匹配改动若让q变小，也必须按新的实际q重新评价，不把阈值冒充实际提取量。

拓扑在这里直接进入匹配费用，不只是更改Kuhn遍历顺序；但线性指派是一个搜索方向，不是将非线性共享资源目标精确变成单次Hungarian。

## 4. 最新算法每一步做什么、为什么这样做

### 4.1 保持两个状态，避免虚拟数据被当成真实服务

[State.__init__](joint_resource.py#L72)保存：

```text
R[s,d]       原生补齐后的服务器辅助残余，单位字节
U[s,d,u]     balance后，源server s的通道GPU u仍需向server d发送的真实字节
P[s]         本阶段源server s选择的目的server
q(P)         R[s,P[s]]的实际最小值
y[s,d,u]     被选中时min(q,U)，其余为0；本轮真实发送量
V            本轮所有真实发送字节之和
```

本轮缩放因子κ=1。U由原生真实payload按server对累加恢复，不能直接拿补齐R替代。自身server匹配只有辅助意义，不产生新增WAN流量；真正机内需求由intrinsic独立处理。

固定路径资源信息从`topology_snapshot`读取；[State._refresh](joint_resource.py#L102)聚合每个有向资源的剩余工作，[State.edge_data](joint_resource.py#L120)缓存给定q下每条候选边的真实字节、资源工作量和传播。缓存不意味着共享负载是常数：它仍随q、U、P变化。

### 4.2 使用同量纲的阶段时间和剩余容量势函数

路径是静态单路径。每条资源e的带宽B以Gbps记录，字节x的工作量为`0.008*x/B`微秒。

```text
w[e] = 本阶段所有经过e的真实字节 / e的带宽
F    = 最大活动真实路径单向传播 + max_e w[e]
L(U) = max_e（剩余全部真实需求在e上的总工作量）
```

F是既定容量近似，不是逐流精确完成时间；不把RTT再加一次。L只是忽略端点匹配、传播和流水线约束的容量下界，不是剩余实际完成时间。

[score](joint_resource.py#L165)有两个已冻结版本：

```text
stage：    F / V
capacity： [F + L(U_after) − L(U_before)] / V
```

二者单位都是“微秒/字节”，没有把毫秒、字节、无量纲压力直接相加。V=0的纯虚拟阶段没有真实服务和网络代价，采用专门零值处理；辅助边数严格下降保证不会无限停留。

stage倾向本轮单位服务高效，却可能留下很差的后续匹配。capacity扣除本轮对剩余关键资源工作的推进，偏好同样真实服务量下较少的额外代价，而不只是本轮短。

这个设计有明确依据，但保证有限：

1. `L_before <= max_e w[e] + L_after`，因此分子非负，且至少覆盖本轮传播代价。
2. 沿完整计划求和，`Σ(F+L_after−L_before)=ΣF−L_initial`，因为最终真实剩余为0。势函数差在总和上会望远镜消去，不是凭空改变通信目标。
3. **逐轮按分子/V贪心不等于最小化全程ΣF**；不同动作留下的支持图、传播付款和真实切分不同。它只是可解释启发式，没有近似比、逐实例非退化或最少stage保证。

当前主算法主要优化网络层F，**未在状态中保留最终目的GPU细分来优化dispatch重叠**。完整流水线时间J是最终评价指标，不能声称本轮已经直接全局优化J。

### 4.3 用阈值允许系数变化，不枚举全部完整分解

[propose](joint_resource.py#L218)先排序R的不同正值，用指派可行性检查二分寻找最大可行阈值。候选最多4个，包含最小正值与最大可行值及中间分位点；阈值只过滤支持图`R>=t`。

本轮不是穷举全部置换、不是随机生成多个完整分解再挑选，也不是每个输入从stage/capacity中选最好。两个版本分别独立生成完整计划，并在所有条件固定比较。

### 4.4 资源价格直接指导匹配生成

[assignment](joint_resource.py#L18)是真正的O(n³)原始—对偶带权Hungarian，`None`表示禁边，可处理负费用。不要与原生函数名为Hungarian、实际是无权Kuhn增广的函数混淆。

每个阈值先由当前剩余最大资源的价格、真实字节和传播信息产生初始指派。[direction](joint_resource.py#L194)随后构造费用：

- 本阶段峰值共享资源上的工作增加，会加价；
- capacity版本中，对下一个剩余瓶颈的有效推进，会减价；
- 使用当前选中关键传播边的分摊价格；这是启发式方向，不是一般离散传播max的精确优化；
- 减去当前效率乘候选真实服务字节，形成比值目标的下降方向。

指派改变后，[State.action](joint_resource.py#L141)重新从原始残余计算实际q，重新计算全部y、F、L_after。**不会直接用线性指派费用决定接受。**

### 4.5 交替环只用于保持合法性并寻找真实评分下降

[cycle_trials](joint_resource.py#L177)比较当前P和带权方向Q，将二者差异分成互不相交的交替环。替换一整个环仍然是完美匹配；它检查完整方向和该方向给出的单个环，不枚举任意端点子集或全部环。

[key](joint_resource.py#L172)依次比较真实评分、更大V、更小F、更大实际q和确定性置换序。只有严格字典序改善才接受；不断重复直到本次方向下无改善。不存在“先删边占满候选，导致交换没有机会”的旧partial搜索路径。

停止只说明当前生成方向和环试探没有找到更好候选；不代表在所有匹配中局部最优，更不是全局最优。

### 4.6 扣减、终止和原生回放

[plan](joint_resource.py#L260)比较本轮各阈值的终止候选，选择一个后更新`R←R−qP`、`U←U−y`，直到R为0。每轮至少消去一个辅助正项，最终检查U也为0。

正确性理由是标准BvN可行性：相等正行列和的支持图满足Hall条件；扣除实际最小值保持非负和相等行列和；不新增正边；`U<=R`的通道覆盖不变量在扣减/裁剪下保持。这是合法性说明，不包装成新的BvN定理。

候选生成后调用[runtime_host compose](runtime_host.cpp#L77)，在新建原生Local状态中再次balance/restore，验证原始GPU来源和目的完整交付，再由[统一evaluate](corrected_study.py#L144)计入balance、intrinsic、network和dispatch流水线。原生基线保持其降序执行；候选构造序与候选降序作为两个明确方法，不混在一起。

### 4.7 实际复杂度与在线边界

设n为server数、m为当前辅助正边数、qv为不同正值数、B<=4为阈值数、I为某个阈值下接受/检查的方向轮数、E为资源数。

- 阈值准备约O(m log m)，最大可行阈值搜索O(n³ log qv)。
- 每个方向需要一次O(n³)带权指派；其真实候选评价还会复制状态、汇总资源，不能把所有代价都简写为一次Hungarian。
- 给定q缓存所有server对的资源向量，当前Python实现约O(n²(g+E))；每个真实候选的状态刷新同阶，单方向至多O(n)个方向环试探。
- 因而可写成“阈值搜索 + B个初始指派 + 各方向轮的指派/状态评价之和”；例如保守计为`O(m log m+n³log qv+B[I+1](n³+n³(g+E)))`，不是紧界。
- **I没有小规模多项式或硬时限证明。** 字典序下降、有限匹配空间保证终止，但“只取4个阈值”不意味着整个算法有固定在线时延。
- 完整分解最多初始m0个stage；预处理、原生Local规划、评估以及Python进程CPU应分开记录。

这正是当前在线目标尚未达标的原因之一，不能简单预言“换C++一定解决所有开销”。
